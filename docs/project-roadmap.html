03 · True sentence streaming

真正的逐句串流，不只是一個布林開關

目標是讓第一句在 LLM 尚未完成整段回答前就開始合成與播放，同時保證插話後不會再冒出舊回合音訊。

目前流程

完整回覆後才說話
STT完整辨識
→
LLM收集所有 token
→
TTS整段文字入列
→
Avatar開始播放

瓶頸：stream_to_avatar=False，而且 assistant_text 只在最後送一次。

建議流程

首句就開始說話
LLM delta持續產生
→
Segmenter語意分句
→
有界佇列最多 2 段
→
TTS / Avatar邊合成邊播

每個 delta、句子與音訊 frame 都攜帶 turn_id，取消後立即失效。

為什麼不能直接改成 True？

LLM 現在跑在 executor。取消 asyncio task 不會停止底層同步 chat_stream；若 callback 直接送 TTS，插話後舊 worker 仍可能繼續排入句子。因此必須把取消令牌與 generation 檢查放進 token → 分句 → TTS 的每一個關卡。

建議建立深層 TurnPipeline 模組

讓 VoiceTurnSession 只知道「開始一個回合」與「取消回合」。同步 LLM、分句、有界佇列、事件順序、錯誤與清理全部藏在模組 implementation 裡。

class TurnPipeline:
    async def run(
        self,
        request: TurnRequest,
        event_sink: Callable[[TurnEvent], None],
    ) -> TurnResult: ...

    async def cancel(self, turn_id: str) -> None: ...

外部 interface 維持兩個動作；ASR、LLM、TTS 與 Avatar adapter 是 implementation 內部 seam。

LLM producer

同步 chat_stream 在 worker thread 產生 delta，透過 thread-safe bridge 放進有界 asyncio queue；每次放入前後檢查 cancellation token。

SentenceSegmenter

硬標點達最小長度立即提交；軟標點、等待時間與最大字數作為無標點回答的保險。

Speech consumer

依序送入 TTS，每段附帶 turn_id、segment_id 與序號；佇列滿時反壓 LLM producer。

Cancellation fence

插話時先使 token 失效，再清文字佇列、TTS 佇列與 Avatar 音訊；任何舊 frame 都必須在輸出前再次驗證。

Incremental events

前端先收到 assistant_delta 更新字幕，完成時再收到 assistant_final，顯示文字與實際語音保持一致。

現有程式可直接利用

  • BaseLLM.chat_stream 已提供 token 串流。
  • TextStreamProcessor 已有標點緩衝雛形。
  • BaseTTS.msgqueue 已能依序處理文字。
  • turn_id / generation 已存在。
  • flush_talk 已能停止多數 TTS 輸出。
  • WebRTC 已能回報 speaking start／end。

開啟現有分句 callback，再補 generation guard

適合快速驗證首句延遲，但 executor 取消、TTS 完成回報、反壓與舊音訊隔離仍較脆弱。應視為 prototype，不建議直接當最終架構。

工程量：低風險：中高可觀測性：低

TurnPipeline ＋取消令牌＋有界佇列

保留現有引擎 adapter，但把回合協調集中到一個深層模組。能同時處理串流、插話、反壓、事件與指標，是目前最好的投入報酬。

工程量：中風險：可控可測試性：高建議採用

所有 LLM／TTS adapter 改成原生 async stream

長期最乾淨，但會同時碰觸所有語音引擎與 Avatar。除非近期要做多使用者 GPU 排程，否則現在投入過大。

工程量：高風險：高長期一致性：最高

驗收條件

首句必須早於完整回答
測試 LLM 尚未結束時，第一個 TTS segment 已送出；記錄 LLM TTFT、首句提交與首音訊延遲。
插話後零舊音訊
取消回合後，即使 executor 還在退 token，任何舊 segment 或 audio frame 都不能抵達 Avatar 輸出。
分句順序與完整性
所有可見文字只增不漏、segment 序號連續，最後拼接內容與完整 LLM 回覆一致。
反壓與錯誤恢復
TTS 慢時佇列不無限成長；任一引擎失敗會送出單一 error，清理資源並重新開啟收音 gate。

05 · Decisions to discuss

開始實作前，先確認四個產品選擇

技術可以調整，但這四項會直接決定語音體感、事件設計與測試範圍。

首句偏快，還是語意偏完整？

太短會像機器逐片念字，太長又失去串流價值。

建議：硬標點優先，700 ms／48 字保底

Markdown 要不要直接念？

畫面需要保留 Markdown，但 TTS 不應朗讀星號、網址與程式碼符號。

建議：顯示文字與可發音文字分離

插話要多徹底？

只清 TTS queue 不夠；LLM worker 與已產生音訊也必須失效。

建議：以 turn_id 形成端到端取消柵欄

先支援哪些 TTS？

所有引擎一次改完風險高，應先選一個快且一個本機引擎驗證。

建議：Edge TTS ＋目前主力本機 TTS

我的建議結論

採用「推薦方案」：先為現有引擎建立 TurnPipeline，不大改每個 adapter；先把取消、事件順序、反壓與指標做對，再逐步把高使用量引擎改成原生 async stream。
