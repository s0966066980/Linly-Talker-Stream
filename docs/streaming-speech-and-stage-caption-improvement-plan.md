# 串流語音分句與舞台字幕顯示改善流程

狀態：已實作；待部署環境進行真實聽感與多尺寸畫面驗收

建立日期：2026-09-03

適用範圍：串流回覆模式、數字人舞台字幕
關聯決策：[ADR 0007](adr/0007-stream-replies-with-turn-isolation-and-audio-clock.md)、[ADR 0009](adr/0009-bounded-stage-caption-window.md)

## 1. 目的

本計畫處理兩個已可穩定重現的問題：

1. 串流回覆過早在逗號或固定字數位置切成 TTS 片段，使語音頻繁停頓、語氣反覆起頭，並可能拆開引號、網址或英文縮寫。
2. 舞台字幕淘汰最舊片段時，舊 DOM 節點仍在動畫期間佔據排版，加上像素捲動與 `20vh` 裁切，導致文字持續往上推或出現半行字。

改善後必須同時維持：

- 串流模式的低首音延遲。
- 以完整可播回覆片段作為播放、字幕及歷史提交邊界。
- 舞台字幕上限與 LLM 回覆生成上限彼此獨立。
- 輪次隔離、中斷、取消與播放提交語意不變。
- 控制台與對話歷史仍保留完整回覆。

## 2. 已確認的現況與根因

### 2.1 語音分句

目前 `src/server/reply_streaming/fragmenter.py` 的預設值為：

- 弱標點最小長度：12 個內容字。
- 軟長度上限：24 個內容字。
- 硬長度上限：32 個內容字。
- 強標點：`。！？；.!?;`
- 弱標點：`，、：,:`

目前演算法同時計算「最早標點邊界」與「最早長度邊界」，再取兩者中較早的位置。因此：

- 一段文字累積 12 字後遇到逗號，就立即形成獨立 TTS 請求。
- 中文文字達到 24 個內容字後，任一中文字元幾乎都會被視為安全邊界。
- 句尾標點後的閉合引號不會一併吸收，可能形成 `完成。` 與 `」下一句` 兩段。
- 目前僅保護數字兩側的標點，沒有完整保護網址、Email、版本號及英文縮寫。

最小重現範例：

```text
輸入：串流模式需要保留完整語意，否則語音會在不自然的位置停頓，而且下一段的語氣也會重新起頭。

目前片段：
1. 串流模式需要保留完整語意，
2. 否則語音會在不自然的位置停頓，
3. 而且下一段的語氣也會重新起頭。
```

```text
輸入：他回答：「今天會完成。」然後離開。

目前片段：
1. 他回答：「今天會完成。
2. 」然後離開。
```

`src/tts/engines/edge.py` 會逐片段獨立呼叫 TTS。片段切得過細時，合成器缺少完整句子的後續上下文，容易在每一段重新建立語氣與停頓。

### 2.2 舞台字幕

目前 `web/stage.html` 的淘汰流程為：

1. 邏輯窗口先淘汰最舊片段。
2. 對應 DOM 節點加上 `.leaving`。
3. 節點執行 260ms 的透明度與向上位移動畫。
4. 動畫結束後才呼叫 `node.remove()`。
5. 容器設定 `overflow-y:auto`，每次新增後執行 `scrollTop = scrollHeight`。

因此邏輯窗口雖然已移除片段，舊節點仍會在正常文件流中佔據高度 260ms。向上位移只改變繪製位置，不會釋放排版空間；配合任意像素捲動後，容器頂部可能停在一行文字的中間。

此外，字數上限與可視高度是兩套獨立限制。相同的 120 字在不同視窗寬度、字級或語言下會產生不同的行數，單靠字數無法保證內容一定落在 `20vh` 內。

## 3. 目標行為

### 3.1 語音

- 完整句尾標點優先形成 TTS 片段。
- 句尾閉合符號必須與前一句一起送出。
- 弱標點是候選邊界，不應只因累積 12 字就立即切句。
- 長度保護應選擇最近且品質最高的候選邊界，不應固定切在第 24 個中文字。
- 網址、Email、版本號、小數與常見英文縮寫不得被標點規則拆開。
- 無標點的異常長文字仍需有硬上限，避免首音延遲與單次 TTS 請求無限增長。
- 分句結果不得改變原始文字順序或遺失任何字元。

### 3.2 字幕

- 被淘汰片段必須立即離開正常排版，不得繼續推動保留文字。
- 舞台不使用可捲動字幕區，也不得依賴任意像素的 `scrollTop`。
- 字數上限仍是主要容量設定，畫面高度則作為第二層安全限制。
- 高度超限時仍只淘汰完整片段，不切斷片段內容。
- 不顯示半行或半個字形。
- 新輪次、取消、斷線及重連的清空行為維持不變。
- 設定仍於下一輪生效，不在正在播放的輪次中途改變容量。

## 4. 整體修改順序

實作必須依下列順序進行，避免同時修改多層後難以確認問題來源：

1. 新增可重現目前問題的失敗測試。
2. 重構串流語意分句器並讓分句測試通過。
3. 驗證各 TTS 引擎仍接收完整、順序正確的片段。
4. 抽離可測試的舞台字幕 DOM 呈現器。
5. 修正淘汰動畫、捲動和高度保護。
6. 執行單元、整合、前端建置及真實語音浸泡測試。
7. 依驗收標準逐項確認後才提交。

## 5. 第一階段：建立失敗測試

### 5.1 分句回歸測試

在 `tests/test_reply_streaming.py` 的 `SemanticFragmenterTests` 增加下列案例：

- 一個含兩個逗號的完整中文句子，在句號到達前不得因第一個逗號過早送出。
- 無標點中文不得固定在第 24 字切開；只有達到新的硬上限才可使用降級切點。
- `。」`、`！」`、`？」`、`.)` 等句尾閉合符號必須留在同一片段。
- `3.14`、`v1.2.3`、`example.com`、`name@example.com` 不得在標點處拆開。
- LLM token 邊界不同時，最終分句結果必須相同。
- `''.join(fragments)` 在忽略既有首尾空白正規化後，必須等於原始回覆。
- 除最後 flush 片段與硬上限降級片段外，不得產生無有效語意邊界的片段。

建議新增一個測試輔助函式，讓測試同時記錄片段與邊界原因：

```python
FragmentDecision(
    text="...",
    reason="strong" | "weak" | "hard" | "flush",
)
```

若不希望改變目前對外回傳型別，可以只在內部保留 decision，`feed()` 仍回傳 `list[str]`，並透過只讀屬性或測試用方法取得原因。

### 5.2 字幕回歸測試

在 `web/tests/` 增加舞台字幕呈現器測試，至少涵蓋：

- 容量超限後，淘汰節點在同一個同步更新週期內已不在正常文件流。
- 離場動畫節點位於獨立 overlay，不影響字幕容器高度。
- 高度超限時會持續淘汰最舊完整片段，直到符合高度或只剩一個片段。
- 不再設定 `scrollTop`，字幕容器也不使用 `overflow-y:auto`。
- 視窗 resize 或字型尺寸改變後會重新執行高度適配。
- reduced-motion 模式會立即移除動畫節點。

若 Node 測試環境無法提供真實排版，可將「是否溢出」抽象為可注入函式，在單元測試中回傳固定結果；另用一次 headless Chrome 測試確認真實 `scrollHeight/clientHeight` 行為。

## 6. 第二階段：改造串流語意分句器

### 6.1 邊界分類

將邊界分成四級：

1. `strong`：完整句尾，例如 `。！？!?`；可立即送出。
2. `weak`：逗號、頓號、冒號與分號；先記為候選位置。
3. `space`：英文單字間空白；只在長度保護時使用。
4. `hard`：沒有其他候選位置時的最後保護，品質最低。

分號建議由目前的強標點降為弱標點。分號通常表示同一句內的並列關係，獨立合成容易產生不必要的句尾語氣。

句尾後應繼續吸收：

```text
" ' ” ’ 」 』 ） ) 》 】
```

以及連續句尾標點，例如 `？！`、`!!`、`……`。

### 6.2 建議門檻

第一版採保守值，後續再依真實語音測試調整：

- `weak_min_chars = 20`
- `soft_limit_chars = 36`
- `hard_limit_chars = 64`

規則如下：

- 找到強標點：立即在吸收閉合符號後送出。
- 尚未達軟上限：弱標點只記錄，不送出。
- 達到軟上限：選擇軟上限附近「最後一個」有效弱標點，不使用最早弱標點。
- 達到硬上限：依 `weak > space > hard` 的順序選擇最接近硬上限的可用位置。
- 無標點中文只有在硬上限才允許降級切分，並記錄 `reason=hard`。
- stream 結束時，以 `reason=flush` 送出剩餘內容。

這組門檻不應直接做成舞台設定。它屬於語音串流策略，應先以固定預設值驗證；若後續確實需要調校，再新增獨立的「語音分句策略」設定，而不是重用舞台字幕字數上限。

### 6.3 保護區段

掃描標點前先辨識不可切分區段：

- 數字、小數與版本號：`3.14`、`1,000`、`v1.2.3`。
- 網址與網域：`https://example.com/a`、`example.com`。
- Email：`name@example.com`。
- 常見英文縮寫：`e.g.`、`i.e.`、`Mr.`、`Dr.`。
- Markdown inline code、HTML 標籤及現有已保護結構。

保護判斷應集中在單一方法，例如 `_is_protected_punctuation(index)`，避免數字、網址與縮寫規則分散在不同分支。

### 6.4 建議演算法

```text
feed(token)
  將 token 加入 buffer
  重複：
    掃描未受保護的標點與空白
    若有 strong：
      吸收連續句尾標點和閉合符號
      emit(strong)
      繼續處理剩餘 buffer
    若內容長度 < soft_limit：
      停止，等待更多 token
    若存在適合的 weak 候選：
      選擇靠近 soft/hard limit 的最後候選
      emit(weak)
      繼續
    若內容長度 >= hard_limit：
      優先在空白切分，否則使用 grapheme 邊界降級切分
      emit(hard)
      繼續
    停止
```

Python 端的長度應以 Unicode grapheme cluster 計算，而不是直接使用 code point 數量。若不增加第三方相依套件，至少必須確保 combining mark、variation selector 與 emoji sequence 不在中間切開；若採用 `regex` 套件，使用 `\X` 並補上相依與測試。

### 6.5 與 TTS 的邊界

`PlayableFragment.text` 必須保留原始標點，TTS 層不得再次做另一套文字分句。第一版只調整分句品質，不同時修改 Edge TTS 的靜音裁切或播放緩衝，避免混淆語意切分與音訊銜接問題。

完成分句修正後進行一次真實聽感測試；若完整句子仍在片段間產生異常停頓，再獨立檢查：

- 每個 TTS 請求尾端保留的自然停頓長度。
- `_StreamingSilenceTrimmer` 是否過度裁切。
- 片段交界是否插入額外靜音幀。

## 7. 第三階段：改造舞台字幕呈現

### 7.1 保持模型與畫面責任分離

保留 `web/src/stageCaptionWindow.js` 作為純資料模型，負責：

- 輪次識別。
- grapheme 字數計算。
- 字數超限時淘汰最舊完整片段。

新增可測試的呈現模組，例如：

```text
web/src/stageCaptionView.js
```

它負責：

- 建立和移除 DOM 節點。
- 可視高度適配。
- 離場動畫 overlay。
- resize 後重新適配。

資料模型可新增明確的 `evictOldest()` 方法，讓 view 在高度超限時要求淘汰完整片段；view 不得直接修改模型的 `fragments` 陣列。

### 7.2 淘汰與動畫

推薦流程：

1. 取得即將淘汰節點的畫面位置。
2. 複製節點到絕對定位的 `.caption-exit-layer`。
3. 立即從 `.reply` 正常文件流移除原節點。
4. overlay 複本只做 180–220ms 淡出，不再推動保留內容。
5. 動畫完成後移除複本。

第一版建議取消向上位移，只保留淡出。若未來恢復位移，overlay 必須允許完整字形顯示，且不得在文字行中間裁切。

`prefers-reduced-motion: reduce` 時不建立 overlay，直接移除原節點。

### 7.3 容器樣式

移除：

```css
overflow-y: auto;
scrollbar-width: none;
```

以及：

```javascript
reply.scrollTop = reply.scrollHeight;
```

改為不可捲動的顯示窗口：

```css
.reply {
  --caption-lines: 5;
  line-height: 1.62;
  max-height: calc(var(--caption-lines) * 1.62em);
  overflow: clip;
}
```

固定完整行數可避免 `20vh` 落在行高中央。實際行數應在 9:16 桌面舞台與行動版各自驗證，必要時於 media query 使用不同的 `--caption-lines`。

保留內容節點使用正常 inline 排版；需要 transform 的動畫只存在 overlay，避免每個 `inline-block` 片段形成不必要的排版盒。

### 7.4 雙重容量限制

每次新增片段後依序執行：

```text
依字數上限更新 StageCaptionWindow
→ 立即移除字數淘汰的 DOM 節點
→ 渲染新片段
→ 檢查 scrollHeight 是否大於 clientHeight
→ 若超高且片段數 > 1，evictOldest() 後重測
→ 直到可完整顯示或只剩單一片段
```

高度限制只負責舞台呈現，不得回頭修改對話歷史或播放提交記錄。

若只剩單一片段仍超高：

1. 套用受控的小字級 class。
2. 必要時把最大行數由 5 行暫時提高到 6 行。
3. 仍不得把單一可播片段從中間切斷。

完成新版分句器後，單一片段通常不會超過約 64 grapheme，因此此降級路徑應非常少見。

### 7.5 ResizeObserver

對字幕容器或舞台註冊 `ResizeObserver`。視窗尺寸、裝置方向或字型載入造成寬度改變時，重新執行高度適配。

重新適配只能淘汰舞台顯示片段，不得重新顯示已經淘汰的舊片段。新輪次開始時仍從第一個已播放片段建立全新窗口。

## 8. 邊界事件與狀態處理

以下事件行為不得改變：

- `assistant_fragment`：在第一個非靜音音訊幀提交後才加入舞台。
- `assistant_fragment_end`：保留現有整體字幕約 3 秒淡出。
- `turn_cancelled`：立即清空窗口、DOM 與離場 overlay。
- `teardown`、斷線與重連：清空所有字幕狀態。
- 新 `turn_id` 的第一片段：取代上一輪舞台字幕。
- 設定輪詢更新：只修改下一輪使用的字數上限。

離場 overlay 必須帶有輪次或 revision 識別。輪次取消或新輪次開始時，舊 overlay 必須一起清除，避免前一輪字幕在新輪次上方短暫閃現。

## 9. 可觀測性

在不記錄實際回覆文字的前提下，新增或擴充串流指標：

- `fragment_boundary_reason_total{reason=strong|weak|hard|flush}`
- 每輪 TTS 片段數。
- 每片段 grapheme 長度分布。
- hard fallback 比率。
- 首個 TTS 片段等待時間。
- 字幕因字數淘汰的片段數。
- 字幕因高度淘汰的片段數。
- 單片段超高降級次數。

驗證期間應特別觀察：

- hard fallback 是否低於所有片段的 5%，理想值低於 1%。
- 平均每輪 TTS 片段數是否下降。
- 首音延遲 p95 不應因本次修改增加超過 300ms；若超過，優先調整 soft limit，而不是恢復 12 字逗號切分。

### 10.4 真實聽感測試語料

至少使用以下類型各測試三次：

- 多個逗號的一般中文長句。
- 短句後接長句。
- 引號中的問句或驚嘆句。
- 含小數、金額、日期與版本號的句子。
- 含網址、Email、中英文混合的句子。
- 64 字以上且刻意沒有標點的文字。
- 使用者中途打斷回覆。
- LLM 回覆尚未完成時取消或重新連線。

聽感紀錄至少包含：

- 是否在語意未完成處停頓。
- 句尾語氣是否重複起頭。
- 片段交界是否有異常長靜音或爆音。
- 字幕出現時間是否仍與實際播放提交一致。

### 10.5 畫面矩陣

至少檢查：

- 360×640 行動版。
- 390×844 行動版。
- 1080×1920 直式螢幕。
- 瀏覽器縮放 80%、100%、125%。
- 舞台字幕上限 20、120、2000。
- reduced-motion 開啟與關閉。
- 字幕單片段、連續多片段及單片段超高。

每一種情境都必須確認沒有垂直 scrollbar、沒有半行字、沒有舊片段推動新片段的動畫。

## 11. 驗收標準

全部條件通過後才視為完成：

- 含逗號的完整中文句子不再固定於 12 字後切成 TTS 片段。

## 15. 追加修正：TTS 逾時造成播放錯誤與畫面凍結

2026-09-03 使用「和我說說大陸的歷史」進行真實 WebRTC 測試時，確認長回答會放大 Edge TTS 首包長尾延遲。原流程在片段進入 TTS 前便登記片段，但兩次合成都失敗時沒有回報終止事件；後續片段雖可播放，輪次仍保留永遠不會結束的片段，最後由播放 watchdog 產生 `playback_error_after_commit`。

同一時間，MuseTalk 為避免在部分語音批次中插入靜音，會在 TTS 尚有工作但 PCM 不足時暫停 `audio_stream.run_step()`。遠端 TTS 等待數秒時，這會讓影片輸出停在上一張嘴型並造成 WebRTC 延遲幀丟棄。

追加修正流程：

1. Edge TTS 最終無首包時，透過 BaseTTS、BaseAvatar 將失敗片段 envelope 回報給 `VoiceTurnSession`。
2. 回報由 TTS worker thread 切回會話 event loop，並再次驗證 `turn_id` 與 generation。
3. 有效失敗片段立即以 `tts_error_before_commit` 或 `tts_error_after_commit` 結束輪次、清空後續媒體，且只提交已播放文字；不得靜默跳過句子，也不得等待播放 watchdog。
4. MuseTalk 對不足 PCM 的合併等待上限為 200ms；超過後允許待機／部分批次繼續推進，避免停留在中間嘴型。
5. Edge 第一次首包等待為 2.5 秒；沒有額外 retry budget 時，第二次等待為 15 秒。收到第一個音訊資料塊後，後續資料塊改用獨立的 15 秒續包逾時。明確的一秒共享 retry budget 仍維持原上限。

回歸測試必須涵蓋：最終 TTS 逾時回報、worker-to-event-loop 終止、只提交已播放文字、200ms 有界等待，以及預設／受限 retry timeout。真實驗收要求指定句子連續三輪均為 `completed`，沒有 fragment 序號缺口，最大影音偏移不超過 250ms，且最大音訊 pacing 落後不超過 500ms。

本次三輪驗收結果全部完成；最大影音偏移依序為 40ms、40ms、120ms，最大音訊 pacing 落後為 88ms、58ms、191ms，影片延遲丟幀為 3、2、4。第三輪第二次 Edge 首包約 7.1 秒才到達，但期間沒有再出現秒級數字人凍結。

## 16. 追加修正：Edge 冷啟動無回應與片段提前終止

2026-09-03 再次分析實機日誌後，確認 Edge TTS 仍有兩個相連問題。第一，第一個程序冷連線的首音實測需要 11.835 秒，後續七次則為 0.498～1.348 秒；原本 1.5 秒加 10 秒的兩次獨立連線都可能在音訊抵達前被取消。第二，第一輪的 1.5 秒逾時被套用到該輪的每一個 websocket 資料塊，而不是只限制首包；遠端串流暫停時會把仍未完成的語音片段收尾，使用者便會聽到提前中斷。

修正流程：

1. 載入設定後立即以背景執行緒預熱 Edge TTS，與 Avatar、LLM 載入重疊；後端宣告 ready 前必須等待預熱執行緒結束。預熱只消費到第一個音訊資料塊，不播放也不保存內容。
2. 預熱失敗不得阻止後端啟動，但必須留下明確 warning；正式回覆仍使用既有的失敗 envelope 回報，不能靜默無回應。
3. 正常第一輪首包逾時調整為 2.5 秒，恢復輪首包逾時調整為 15 秒，以涵蓋本機觀測到的 11.835 秒冷連線。
4. 一旦收到第一個音訊資料塊，同一輪後續資料塊一律使用獨立的 15 秒續包逾時，不得再套用 2.5 秒首包逾時。
5. 已提交 PCM 後仍禁止從頭重試並拼接樣本，避免重複語音與時間軸跳動；續包真的超過 15 秒時才按既有 fail-closed 規則結束。

回歸測試必須涵蓋：預熱只取首個音訊資料塊、非 Edge 引擎不啟動預熱、ready 前等待預熱完成、恢復等待至少 15 秒，以及首音後切換到續包逾時。實機驗收需在重啟後立即送出第一個指定長句，接著連續多輪送出長回答，確認沒有 `tts_exhausted_before_audio`、沒有 `tts_error_*`，且所有片段都有 start/end 邊界。
