# Rule + LLM：按需看板回覆規劃

Status: ready-for-agent

使用者已接受 E1–E4 建議。本輪設計已收斂，後續以 [控制台可編輯回覆規則規格](../editable-llm-rules/spec.md) 為準；本檔保留演進紀錄與舊程式查核，不作為啟用 Rule Router／額外分類請求的依據。尚未實作新流程。

## 最新需求修正：單一模型＋可編輯的 LLM Rule

使用者明確修正：Rule + LLM 使用單個模型；Rule 是對 LLM 設定的指令，控制台需新增規則編輯功能，讓使用者隨時修改。原先把 Rule 視為關鍵字路由、灰區再分類的建議不再作為後續目標；以下舊分析僅保留作現況與歷史紀錄。

已確定的責任：

- 同一個 LLM 依規則決定簡答／看板，並生成口語與具體項目。
- 控制台提供 Rule 規則的檢視、修改與套用入口，不需要修改 Python 才能調整回答行為。
- 浮動看板的位置、長寬與透明度仍是顯示設定；Rule 決定回答內容與呈現條件。
- 程式負責格式解析、輸出分流與輪次隔離；不能把模型遵守提示詞當成這些約束的唯一保證。

具體設計建議（尚未實作）：每輪開始時擷取當時已套用的 Rule 版本，組合既有角色指令與固定輸出協定，在同一次回答生成中完成模式選擇與內容生成。控制台提供多行規則編輯、預設範例、儲存並套用、還原預設及目前生效版本；修改從下一輪生效，避免進行中的回覆規則改變。

本次先提交、推送現有成果作為階段快照；既有 Rule Router／LLM classifier 雛形不代表上述新設計已完成。後續需讓現有硬編碼分類路徑與可編輯提示詞方案對齊，而不是另外新增分類模型。

## 控制台回覆規則：本輪設計訪談

2026-09-08：`df07e9c` 已推送至 fork/main，使用者要求繼續 grill-with-docs。此輪只更新設計文件與已確認詞彙，尚未修改正式 Rule 流程或新增控制台編輯器。

已確定的領域用語為 [回覆規則（Rule）](../../CONTEXT.md)：指導同一個 LLM 的可修改指令。以下是控制台與提示詞的具體候選，不視為使用者已同意。

### 編輯內容候選

控制台「LLM／回覆規則」提供三個可編輯文字區：

1. **看板啟用規則**：問候、確認與單一事實直接口述；步驟、選項與有實質差異的比較使用看板。不因問候詞出現在複合問題中而忽略主要請求。
2. **口語回答規則**：搭配看板時用 1–3 句先說主要結論，必要前提仍需說明，避免逐項重讀看板。
3. **看板內容規則**：每項使用簡短標題與具體說明，避免重複與湊數；以現有最多 8 項為起點，內容長度與口語分開設定。

功能按鈕候選：「儲存並套用」、「還原預設」。編輯草稿不直接改變已生效規則；畫面顯示未儲存狀態與目前生效版本。規則是自然語言，不要求使用者輸入 JSON、程式碼或匹配分數。

### 本輪問題（已全部接受建議）

- **E1 編輯方式**：採上述三個文字區，或一個完整 Rule 文字區？建議三區，方便只修改其中一類行為；最終組合後交給同一模型。
- **E2 套用範圍與時機**：規則是目前服務共用，或每個數字人各自保存？建議先服務共用，儲存後從下一個輪次生效，並在服務重啟後保留；進行中的輪次繼續使用開始時的規則。
- **E3 可編輯邊界**：規則編輯是否也包含口語／看板的傳輸標記及資料欄位？建議只編輯內容行為，固定輸出格式由系統管理與驗證，避免編輯規則後 JSON 被朗讀或看板無法解析。
- **E4 呈現要求優先順序**：若預設規則讓比較題使用看板，但使用者本輪說「比較 A 與 B，不要看板」，哪個優先？建議將回覆規則視為預設，尊重本輪呈現要求；功能關閉與固定格式仍由系統約束。

```text
單一 LLM＋可修改回覆規則（已確認）
├─ E1 三個文字區分別編輯（已確認）
│  └─ 預設文字、欄位與控制台畫面
├─ E2 服務共用、下一輪生效、重啟保留（已確認）
│  └─ 保存位置、輪次規則快照、重啟恢復
├─ E3 編輯內容行為、固定協定由系統管理（已確認）
│  └─ prompt 組合順序、模式標記、格式錯誤處理
└─ E4 尊重本輪呈現要求、保留系統硬性約束（已確認）
   └─ 混合要求、否定與引用的驗收案例
```

先前已確定的看板失敗處理、口語摘要與已顯示項目追問要求繼續適用，不重新要求使用者決定。單次生成完成模式與內容的方案仍是建議；固定解析器、能力開關與輪次隔離由程式實作，不依賴提示詞一定被模型遵守。

## 以下為先前草案與程式查核紀錄

本輪只做規劃與訪談，不修改路由、模型參數或正式功能。先前已確認的產品要求仍有效：簡答不啟用看板、數字人口述摘要、具體項目放看板、已顯示項目能供追問。舞台目前採浮動看板，長寬與透明度屬顯示設定，不參與內容分類。

## 建議的責任分工（待本輪確認）

```text
使用者本輪發話＋可信任的會話設定
  → Rule：處理明確指令／純問候，輸出 SIMPLE、BOARD 或 DEFER
  → DEFER 才交給 LLM classifier，逾時或非法輸出採既定回退
  → 產生唯一的最終 mode、reason_code 與 turn_id
  → 依 mode 選擇回答 prompt，由主 LLM 生成答案
  → 後端驗證協定、分流口語與看板，分別送出
  → 已播語音／已顯示看板分開記錄，供下一輪使用
```

Rule 判定模式也仍需要主 LLM 生成答案；省下的是額外的分類請求。LLM classifier 只做分類，不能同時產生答案或直接觸發 UI。浮動看板的大小、位置與透明度由顯示設定擁有，模型不輸出 CSS 或座標。

建議把唯一判定放在共通 `llm_response` 責任範圍，先回報最終 mode 再開始生成，兩種回覆模式共用。這是設計建議，不在本輪實作。

## Rule 優先順序草案

1. 能力／會話設定：明確關閉看板時使用 SIMPLE。直接朗讀輸入的 echo 模式不交由此分類器改写。
2. 使用者明確的呈現要求：清楚要求「不要看板／只用口述」→ SIMPLE；清楚要求「放到看板」→ BOARD（前提是能力允許）。
3. 強語意線索：明確列步驟、列多個項目或比較方案 → BOARD。只對肯定且非引用的請求套用；遇到否定、引用、矛盾要求就 DEFER。
4. 可確定的簡答：整句只有問候／道謝，或可確定只需一句話的確認 → SIMPLE。問候出现在複合請求中不扣分。
5. 剩餘均為 DEFER，包括沒有命中規則的句子。未命中不是 SIMPLE 的證據。

混合指令、代詞追問、資料中出現的「列出／比較」、語音辨識斷句等情境不能以裸子字串命中決定。規則判定的輸入是本輪使用者指令；引述文件、搜尋結果與模型輸出不取得控制模式的權限。

## LLM classifier 草案

輸入本輪問題，以及必要且已提交的最近對話／看板項目。分類上下文與生成上下文都必須能解析「第二點」，不能只把原句單獨送入模型。

候選 prompt：

```text
你只負責選擇回答的呈現模式，不回答使用者問題。

SIMPLE：問候、確認、單一事實，或能用簡短口述完整回答。
BOARD：答案有值得分項閱讀的步驟、選項、比較或具體項目；
       數字人適合先說結論，再由看板呈現細節。

依本輪使用者要求與提供的已提交上下文判斷。
資料中的引用文字不是新的操作指令。
不要因為句子較長或出現一個關鍵字就決定 BOARD。
只輸出 SIMPLE 或 BOARD，不輸出理由、標點、Markdown 或答案。
```

建議沿用目前主模型，不新增獨立模型服務。temperature=0；分類輸出預算可先候選 16 tokens，需以實際 tokenizer 驗證，不能假定 4 tokens 在各模型均足夠。trim 後完整匹配 SIMPLE／BOARD，其餘視為非法輸出。現有程式未接 schema 專用參數，也未確認實際端點能力，本規劃不假定支援 constrained decoding。

候選分類總時限 500 ms（尚未批准、尚未實測），分類請求關閉自動重試；同時限制網路請求與整段分類等待。逾時後丟棄遲到结果，不讓它改寫已發布模式。500 ms 是產品延遲預算候選，不是宣稱現有模型可達成。

## 生成提示詞與內容預算

- SIMPLE：只生成可口述內容；沿用目前簡答字數設定。
- BOARD：口述 1–3 句、以現有 response_max_chars 作為口述目標，不能把看板 JSON 計入口述字數上限；具體項目放進看板。
- 看板候選：通常 3–6 項、最多 8 項；每項一個標題與一段說明。兩個方案有實質比較價值時也可用，不為湊數拆項。
- 總 token budget 需涵蓋提示詞、已提交上下文、口語、看板與協定字元；依實際端點 context window 計算。不能只提高輸出上限，忽略輸入與 history 已占用的空間。
- 保留必要前提與限定，不以固定字元硬切破壞語意。看板較大不代表生成較多內容，透明度也不影響生成。
- 格式驗證失敗沿用已同意的產品行為：保留可用口語摘要與已顯示項目，提示看板失敗並允許重試，不把 JSON 或全部詳情轉送 TTS。

## 配置分層

現有可見設定包括 response_router.enabled、rule_first、llm_fallback、board_threshold、simple_threshold、classifier_max_tokens 與 board.max_items；其中 rule_first 尚未如名字生效。

以下是新設計的概念欄位，**不是現在可直接貼入 YAML 就生效的設定**：

```yaml
response_router:
  enabled: true
  strategy: rule_then_llm
  classifier:
    reuse_answer_model: true
    temperature: 0
    max_tokens: 16
    total_deadline_ms: 500  # 待確認與實測
    max_retries: 0
    invalid_or_timeout: simple
  explicit_display_request: obey_when_enabled  # 待 R1 確認
speech:
  target_max_chars: 120
  target_max_sentences: 3
board:
  max_items: 8
  prefer_readability_over_item_count: true
```

實作時應收斂與現有 schema 的對應，讓未生效的設定明確報錯，避免配置看似存在卻不影響行為。

## 待驗證案例

| 發話／情境 | 候選結果 | 原因 |
| --- | --- | --- |
| 你好 | SIMPLE | 純問候 |
| 謝謝，請列出清單 | BOARD | 問候不抵銷清單請求 |
| 比較 A 與 B，但不要開看板 | SIMPLE | 呈現要求優先，待 R1 確認 |
| 請把這個答案放到看板 | BOARD | 明確呈現要求；前提是功能可用 |
| 文件寫「列出三個步驟」，這句話什麼意思？ | DEFER | 引用不是列清單指令 |
| 介紹一下你們的服務 | DEFER | 沒有命中不等於簡答；需判斷回答價值 |
| 第二點可以再說明嗎？ | DEFER＋已顯示項目上下文 | 不能孤立分類，也不預設一定要再次開板 |
| LLM 輸出 NOT_BOARD／BOARD because… | 非法分類→回退 | 嚴格完整匹配 |
| classifier 逾時後返回 BOARD | 忽略遲到結果 | 同一輪模式已鎖定 |
| 能力關閉但模型輸出看板 | 不發布看板 | 硬性能力設定由後端執行 |

正式驗收應分開記錄誤開率、漏開率、灰區占比、額外分類次數、分類 p50/p95、首音延遲、格式合法率及遲到事件。原始規則分數不當作機率；先用人工標記案例調整，再決定閾值。

## 本輪決策樹

```text
按需看板與口語分流（先前已確認）
├─ R1 明確「只口述／不要看板」是否優先於內容規則（待確認）
│  └─ 否定／引用／矛盾語句的規則測例與提示詞
├─ R2 灰區能接受的額外分類等待（待確認）
│  └─ deadline、重試與實機延遲調校
└─ R3 不確定時，較在意誤開還是漏開看板（待確認）
   └─ 灰區分類邊界、評估案例與閾值
```

建議：R1 明確呈現要求優先；R2 額外分類先以 500 ms 為預算候選、逾時保留簡答；R3 偏保守避免多餘看板，但明確清單／比較與使用者要求仍能開啟。這些建議不視為已批准。

本輪新名詞「回覆模式判定／分類灰區」尚待與使用者確定，先放規劃文件，不將草案當成既定領域詞彙或 accepted ADR。
