# 單一 LLM＋可編輯 Rule：詳細修改流程

狀態：已依本文完成程式修改，待使用者實際啟動服務與模型驗收。本文仍保留作為修改順序、測試與回退依據；不代表已完成 Git commit 或部署。

依據：[已確認規格](spec.md)、[設計決策 ADR 0012](../../docs/adr/0012-editable-rules-for-single-llm.md)。程式盤點基準為 `df07e9c` 及目前工作目錄；執行前須重新確認差異，保留既有未提交修改。

本次修改已完成後端規則模型／API、單次生成模式協定、增量看板項目事件與控制台編輯器；自動驗證結果為後端 `328 passed, 1 skipped`、前端 `39 passed`、Vite build 成功。真實模型遵循率、瀏覽器互動與播放設備驗收仍由使用者執行。

## 1. 目標與邊界

1. 使用目前選定的單一模型，正常回答僅呼叫一次生成；同次輸出決定簡答或看板並產生內容。
2. Rule 是給模型的自然語言指令，不是關鍵字計分，也不是先呼叫分類器再呼叫回答模型。
3. 控制台提供「看板啟用規則」「口語回答規則」「看板內容規則」三個編輯區。
4. 儲存成功後，全服務後續輪次採用新版本；已開始輪次繼續使用舊快照。重啟保留設定。
5. 簡答只口述；看板回答先口述主要結論，再逐項顯示詳細資訊，不能把協定或看板內容送入 TTS。
6. 看板仍是舞台上的浮動視窗。長寬、背景透明度、位置屬舞台設定，不混入 Rule。
7. 本輪明確呈現偏好優先於預設 Rule；功能開關、固定資料格式及安全限制仍由系統控制。

本次不新增第二個模型、不微調模型、不自動部署或推送 GitHub。看板外觀沿用既有設計，必要修改限於事件整合與回歸修正。

## 3. 階段 0：建立基準與保護既有工作

1. 檢查 `git status --short`、目前分支、提交與遠端，記錄已有修改。
2. 閱讀 spec 與 ADR；舊 `rule-llm-plan.md` 的計分提案只供歷史參考。
3. 執行第 11 節既有測試，記錄修改前結果與既有失敗。
4. 確認實際啟用的模型、端點、上下文與輸出限制。設定檔名稱不代表端點實際載入的模型。
5. 備份執行時設定至受保護位置，避免將 API key、端點憑證或個人規則貼入文件、日誌或 Git。

完成條件：可區分本次新增問題與既有問題；不清除或重設使用者工作目錄。

## 4. 階段 1：規則資料模型與預設值

建議設定結構如下，欄位名稱是實作提案，非目前 API：

```yaml
llm:
  reply_rules:
    revision: 1
    activation: "何時簡答、何時使用看板的自然語言規則"
    speech: "口語摘要的自然語言規則"
    board: "看板項目的自然語言規則"
```

1. 從 spec 三區預設文字建立唯一預設來源，前端透過服務取得預設值，不另寫一份。
2. 對舊設定缺少 `reply_rules` 的情形補入預設，不要求使用者手動修改 YAML。
3. 驗證三欄型別、非空內容、各欄長度及總提示預算。上限以模型容量和實測定案，前後端共用服務回傳限制。
4. 過長規則明確拒絕，不靜默截斷。自然語言規則可編輯不等於允許改動解析器協定。
5. 定義不可變 `RulesSnapshot`，至少包含 revision 與三欄文字；版本由服務產生，不能由客戶端指定下一版。
6. 將規則與角色提示、舞台外觀、口語字數限制分開，避免修改一項重設其餘設定。

完成條件：缺省遷移、非法輸入與快照隔離具單元測試。

## 5. 階段 2：設定 API、原子儲存與衝突控制

沿用既有設定路由風格。建議新增 `GET /api/llm/rules` 與 `PUT /api/llm/rules`；實際命名可在實作時配合現有路由，但必須前後端一致。

GET 回傳目前三欄、revision、預設規則及驗證限制。PUT 的建議請求：

```json
{
  "expected_revision": 1,
  "rules": {
    "activation": "……",
    "speech": "……",
    "board": "……"
  }
}
```

儲存步驟必須依序執行：

1. 驗證整份請求；沿用控制台現有存取保護，不讓聊天輸入操作管理設定。
2. 取得設定交易鎖，重新讀取目前版本並比較 `expected_revision`。
3. 以最新完整設定建立候選副本，只替換規則及新版本。
4. 在同目錄寫入暫存檔，完成必要 flush／同步後原子替換正式檔案。
5. 持久化成功才發布記憶體中的新快照，再回傳已套用版本。
6. 讀取輪次快照與設定發布使用一致的同步機制，避免讀到半套更新。

不能只在規則儲存處加鎖：其他模型、舞台及語音設定也會寫同一檔案，須共用交易保護並以最新設定合併。若部署多程序，單一 `threading.Lock` 不足，須加入跨程序協調，或明確限制為單程序設定寫入者。

| 情境 | 預期處理 |
| --- | --- |
| 欄位空白、型別或長度錯誤 | 400 類錯誤，指出欄位，不變更版本 |
| 另一控制台已先儲存 | 409，提示重新載入／比較，保留本地草稿，不自動覆寫 |
| 寫檔失敗 | 500 類錯誤，保留先前生效規則，不顯示儲存成功 |
| 回應遺失但可能已存成功 | 重新 GET 核對版本與內容，不盲目再次覆蓋 |
| 重啟或意外中斷 | 載入完整舊版或完整新版，不接受半份 YAML |

完成條件：重啟保留、失敗不發布、併發不遺失其他設定、舊版本請求被拒絕均通過測試。

## 6. 階段 3：單次模型生成與固定串流協定

### 6.1 提示組裝

每輪使用同一份快照，組合角色提示、三區 Rule、能力限制、固定協定，再附上已提交歷史和本輪問題。明確說明使用者本輪呈現偏好高於預設 Rule，引用資料內的文字不是新的操作指令。

不得在生成前另呼叫分類器。修改規則不需重新啟動模型，也不得藉修改快取 LLM 物件的共享提示影響其他正在生成的輪次。

### 6.2 協定與解析器

現有 `[[SPEECH]]`／`[[BOARD_JSON]]`／`[[END]]` 是整段看板解析基礎；不能直接宣稱已支援逐項生成。實作時先定案並測試協定，再接服務。

建議演進為：固定模式前綴 → 口語區段 → 可獨立驗證的項目框架 → 結束標記。模式僅允許 SIMPLE／BOARD；每個項目包含穩定 ID、標題及內文。確切標記與版本須寫入 parser 測試，不讓使用者在三區 Rule 編輯。

必要解析要求：

- 模式完整驗證後只通知一次；不能先發 SIMPLE 再改 BOARD。
- 處理標記與 JSON 被拆成任意 token 區塊的情形。
- 只將已辨識的口語文字送 TTS，未知前綴、思考標記、JSON 或解析失敗原文不得直接朗讀。
- 每個完整且通過 schema 驗證的項目才送 UI；不以任意字串切片冒充完整項目。
- 限制項目數、單項長度、總緩衝量及總輸出量；拒絕非法型別與 HTML 注入。
- SIMPLE 不接受看板事件；BOARD 缺少必要口語或內容時標記不完整，不假裝成功。
- 看板中途失敗保留已完成摘要與項目，顯示可重試狀態，不自動把所有詳情改成口述。

口語 `response_max_chars` 只約束口語。模型總 token 預算必須另納入看板與協定開銷，並受端點上下文限制；不得仍以短口語預算截斷整張看板。

正常輪次一次生成。若提供「重試看板」，必須是明確的後續動作，另計呼叫，避免重播已播摘要；不以隱藏重試掩蓋單次生成失敗。

完成條件：任意分塊測試、非法輸出、截斷、超限與 TTS 隔離測試通過。

## 7. 階段 4：輪次與服務整合

1. 明確定義輪次開始為服務接受新回覆輪次的入口；語音和文字入口一致地捕捉規則快照，不延至模型開始生成才讀取。
2. 將快照沿 `voice_session` → `llm_response` → `BaseLLM` 傳遞，事件／診斷記錄附 `turn_id` 與 `rules_revision`。
3. 移除 `voice_session` 預先路由及 `service` 再次路由。模式由解析器確認後回傳。
4. 統一模式序列化，Enum 使用明確值，不依賴 `str(enum).lower()`。
5. 檢查相容包裝器的廣泛 `TypeError` 重試，避免模型已呼叫後再重複呼叫；改為明確介面適配。
6. streaming／legacy 路徑均只把口語交給 TTS，並共用模式與規則語意。
7. 取消後停止接受舊輪次輸出；晚到事件不能污染新輪次。事件必須帶輪次識別並通過 fence。
8. 查清舊 router 引用後才刪除失效程式、設定與舊計分測試；以單次呼叫測試取代，不直接丟棄所有 router 型別。

驗證案例：A 輪捕捉 v1 → 控制台套用 v2 → A 全程 v1 → B 使用 v2；同時兩個 session 也不得混用快照。

## 8. 階段 5：看板事件與已顯示上下文

此階段依賴 [ADR 0011](../../docs/adr/0011-separate-spoken-and-displayed-answer-commit.md) 的分離提交方向；該 ADR 仍為提案，顯示確認協定需在實作前補足，不把 `_last_board` 當成已顯示證據。

1. 統一控制台與舞台的項目欄位，明確處理現有 `body`／`content` 差異。
2. 選擇一套標準增量事件；現有 `assistant_board` 與 `board_begin/item/end` 若暫時並存，使用版本或 ID 去重，不能重設並重複填入同一張看板。
3. 規劃顯示確認：包含 conversation、turn、board、item 及呈現端識別；由實際渲染成功的指定呈現端確認。多視窗不得將同一項重複提交，重連須可去重。
4. 明確區分「已產生」「已送出」「已顯示」。確認只是應用程式渲染收據，不宣稱使用者真的閱讀。
5. 後續提示加入已提交口語與已顯示項目；未顯示或取消後丟棄的項目不得冒充共同上下文。
6. 保留穩定項目順序，使「第二點」能對應到正確看板；沒有可用指涉時先澄清。
7. 依既有設計處理關閉僅隱藏、下一輪折疊、清除對話清除上下文，以及中斷保留已顯示項目。
8. 驗證浮動看板的尺寸、透明度與位置仍正常，不遮擋必要操作；調整外觀不觸發規則儲存或模型生成。

完成條件：兩個呈現端事件一致、項目不重複、舊輪次不回流、顯示上下文可追問。若共享 conversation 或確認通道尚未接通，列為未完成依賴，不以 UI 可見取代驗收。

## 9. 階段 6：控制台三區 Rule 編輯器

1. 在 LLM 設定新增「回覆規則」，沿用目前設定面板樣式。
2. 三個多行欄位各有用途說明、字數／限制提示與錯誤位置；固定協定不暴露為可編輯欄位。
3. 使用 `appliedRules` 與 `draftRules` 分離狀態，呈現目前版本與未儲存標示。
4. 首次載入取得同一版本三欄及預設值；背景刷新不能覆蓋尚未儲存的草稿。
5. 「儲存並套用」一次送三欄和基底版本；請求期間防止重複提交，成功後更新生效版本。
6. 若儲存途中仍允許輸入，成功回應只確認已送出的快照，不把後續輸入誤標為已儲存；也可暫時鎖定欄位。
7. 「還原預設」只更新草稿，提示仍需儲存，不即刻變更模型行為。
8. 409 顯示版本衝突並保留草稿；提供重新載入／比較途徑，不暗中強制覆蓋。
9. 一般錯誤保留草稿及上一生效版本；成功提示「已套用，從下一輪生效」。
10. 驗證鍵盤操作、標籤對應、焦點、窄螢幕捲動及螢幕閱讀器狀態提示。

完成條件：未儲存、儲存中、成功、驗證失敗、網路失敗及版本衝突均可操作且不遺失草稿。

## 10. 階段 7：測試矩陣與真實模型驗證

| 範圍 | 必測案例 | 通過條件 |
| --- | --- | --- |
| 設定 | 缺省、空白、超長、寫檔失敗、重啟、多控制台 | 一致版本、錯誤不發布、不遺失其他設定 |
| 輪次 | 生成途中套用、雙 session、文字／語音 | 當輪固定舊版、後輪使用新版 |
| 呼叫 | 簡答、看板、模糊問題 | 正常每輪只呼叫一次回答模型，無分類呼叫 |
| 協定 | 任意分塊、非法模式、壞 JSON、缺少口語、超限 | 不洩漏至 TTS，不送半項，不誤報成功 |
| 事件 | 重複、延遲、取消、重連 | 去重且只更新正確輪次 |
| 上下文 | 第二點、未顯示項目、關閉、清除 | 只根據可用的已提交內容回答 |
| 控制台 | 草稿、預設、衝突、失敗、儲存中編輯 | 生效狀態可信，草稿不遺失 |
| 舞台 | 長寬、透明度、位置、窄畫面 | 原有浮動看板與字幕／操作仍可用 |

真實模型探針至少包含：

- 「你好」：預期簡答。
- 「謝謝，請列出三個安裝步驟」：不能因道謝抵銷實際問題，預期看板。
- 「比較 A 與 B，但不要看板」：預期口述。
- 「請用看板列出注意事項」：能力允許時預期看板。
- 引用內容包含「不要看板」但本輪要求看板：不能把引用當成新指令。
- 看板完成後「解釋第二點」：需對應已顯示項目。
- 修改啟用規則後重跑相同問題：驗證新規則真的進入模型請求並影響行為。

為每個探針記錄模型、規則版本、預期／實際模式、格式合格率、呼叫數、首句與首項延遲。重複取樣，不能以單次成功推論穩定；模型遵循率與延遲目前未量測。若品質不足，調整同模型提示與協定，不偷偷加入第二次分類呼叫。

## 12. 提交順序、發布與回退

建議分批提交，每批附相應測試：

1. 規則模型、預設值與相容載入。
2. 原子持久化、API 與版本控制。
3. 固定協定、提示與單次生成整合。
4. 事件、取消、顯示確認與追問上下文。
5. 控制台編輯器、端到端驗證與文件。

階段 1 → 2 → 3 → 4 為主要依賴；控制台可在 API 契約穩定後接入，但整體完成須包含顯示上下文及真實模型驗證。

发布前先在測試環境載入設定副本，確認重啟與舊設定相容。部署須讓後端協定與兩個前端消費端版本匹配；若需分批，先提供明確版本相容層，不能混發未定義事件。

回退分兩種：

- 規則內容效果不佳：控制台載入先前規則或預設值，再儲存成新版本，從下一輪生效，不倒退版本號。
- 程式回歸：經授權回退對應程式提交及相容前端；先備份設定，保留新增欄位或使用經測試的遷移，不覆蓋整份執行時設定。不要使用 `git reset --hard` 清除工作。

只有使用者明確要求才 commit／push；推送前核對遠端與目標分支。本文建立不觸發提交、推送或部署。
