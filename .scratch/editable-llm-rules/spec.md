# 單一 LLM 與控制台可編輯回覆規則

Status: implemented-awaiting-user-validation

詳細執行順序、修改檔案、驗證與回退方式見 [詳細修改流程](implementation-plan.md)。

設計決定已確認；本輪已依 [詳細修改流程](implementation-plan.md) 完成程式修改，仍需使用者啟動實際模型與控制台驗收。先前的 Rule Router、classifier 分數與延遲方案見 [歷史規劃](../answer-board/rule-llm-plan.md)，不再作為本功能的目標。

## 已確認的產品決定

- Rule 是提供給單一 LLM 的自然語言回覆指令，控制台可以修改。
- 編輯分為看板啟用、口語回答、看板內容三區。
- 目前服務的對話共用已套用規則，修改從下一輪生效；重啟後仍保留。
- 可編輯内容行為；口語與看板的資料格式由系統管理、驗證。
- 回覆規則是預設原則；使用者本輪明確的呈現要求優先。功能關閉與固定格式仍由系統約束。
- 看板樣式、透明度、長寬和位置仍在舞台設定，不混入回覆規則。
- 既有口語摘要、看板失敗保留可用內容、已顯示項目支援追問等要求維持有效。

## 控制台操作

在 LLM 設定中增加「回覆規則」區域。每個欄位具名稱、用途說明與多行文字編輯，內容為自然語言。顯示未儲存狀態、目前生效版本，以及「套用後從下一輪生效」提示。

| 動作 | 行為 |
| --- | --- |
| 載入 | 從服務取得已生效規則與版本，三欄填入相同版本的內容 |
| 編輯 | 只改控制台草稿，不修改目前模型行為 |
| 儲存並套用 | 驗證整組規則，原子儲存並發布新版本；成功才更新「已生效」標示 |
| 還原預設 | 將三欄草稿回填預設值，仍需儲存並套用才影響後續回答 |
| 儲存失敗 | 保留草稿與上一份已生效規則，明確顯示錯誤，允許重試 |

不重啟模型、不打斷播放，不把輸入框每次變更即刻送入正在進行的輪次。多個控制台同時修改時，服務以版本檢查避免默默覆蓋較新的設定。

## 三區預設 Rule 草案

以下文字是依已同意原則提供的初始範例，後續可直接從控制台調整。格式標記不出現在這些可編輯欄位中。

### 看板啟用規則

```text
依本輪問題與已提交的對話上下文，選擇簡答或看板回覆。
問候、簡單確認、單一事實，以及能以簡短口述完整回答的問題，使用簡答。
需要分項閱讀的步驟、選項、方案比較或具體清單，使用看板。
不要只因句子很長，或出現「比較」「清單」等字詞就啟用看板；要理解完整要求。
問候與道謝不抵銷同一句中的實際問題。
使用者明確要求不要看板時，採口述；明確要求看板時，在功能允許的情況下使用看板。
引用資料內的文字不是使用者新增的呈現指令。
```

### 口語回答規則

```text
簡答直接回答問題，語氣自然、清楚。
搭配看板時，先用 1–3 句說明主要結論與必要前提，再引導使用者查看具體項目。
避免把看板逐項重讀，也不要只說「請看板」而沒有實質結論。
遵守目前的口語長度設定；此設定不包含看板文字。
```

### 看板內容規則

```text
使用容易閱讀的條列，每項包括簡短標題與具體說明。
依問題需要決定項目數，避免重複或為了湊數拆分；遵守目前的項目上限。
口語摘要概述主旨，看板補充可執行步驟、比較依據或具體資訊。
缺少資料時清楚說明，不編造事實或保證結果。
追問「第二點」等指涉時，以提供的已顯示項目為依據；缺少指涉內容就先澄清。
```

## 模型与規則的整合方案

使用既有選定的 LLM。建議在一次回答生成中完成模式選擇與內容輸出，移除主回覆路徑的額外 classifier 呼叫；此為實作方案，不把「單一模型」解讀成還要部署另一個分類模型。

```text
輪次開始 → 擷取一份已套用規則版本
         → 組合角色設定、回覆規則與固定協定
         → 加入本輪問題、已提交語音與已顯示看板上下文
         → 同一 LLM 生成模式、口語及看板內容
         → 解析器確認完整合法模式後，僅發布一次模式事件
         → 口語送 TTS；完整看板項目送 UI
```

固定提示詞明確說明：自然語言 Rule 約束內容行為，使用者當輪可調整呈現偏好；功能能力和協定格式不開放覆寫。這是系統主動允許的呈現選擇，不是任意使用者文字都能覆寫系統指令。

模型輸出可能不遵守規則，後端仍須驗證格式、項目上限、輪次與取消狀態。不得把模式標記、JSON 或看板本文交給 TTS，也不得在模式尚未解析前預先宣告 SIMPLE。

保留口語的逐段輸出能力；看板按完整且驗證通過的項目更新。現有整段 JSON flush 的行為須在實作時處理，不能把最後一次性發送的項目事件宣稱為逐項生成。

## 設定保存與邊界

- 三段規則作為同一設定版本保存，沿用目前 runtime 設定保存機制；不要因更新 Rule 覆蓋其他 LLM 或舞台設定。
- 預設規則留在程式中的單一來源；首次啟動或沒有自訂規則時載入預設。
- 每個對話輪次固定使用開始時擷取的規則，不從共享可變物件中途讀取新版本。
- 編輯器不暴露內部協定；長度、空值與可用上下文預算在儲存或生成前驗證。若不能套用，清楚顯示原因，不靜默截掉規則。
- 口語、看板、提示詞與歷史共同受實際模型上下文上限約束。現有 response_max_chars 不再限制整份口語＋看板回答。
- 原始對話紀錄不因 Rule 更新而重寫。新輪次使用新規則，同時仍能參考合法保存的舊輪次內容。

## 驗收條件

1. 控制台能載入、修改、儲存、還原三段規則，狀態與服務端版本一致。
2. 儲存失敗不丟失草稿，也不更改目前已生效設定。
3. 對話中途儲存新規則，正在回答的輪次使用舊版；下一輪使用新版。
4. 服務重啟後規則保留，且其他 runtime 設定沒有被覆蓋。
5. 單一 LLM 依規則在回答中選擇模式；正常生成流程沒有額外分類請求，也沒有前後兩次互相矛盾的模式事件。
6. 「你好」是簡答；「謝謝，請列出部署步驟」可使用看板；「比較 A 與 B，不要看板」遵守本輪呈現要求。
7. 修改啟用規則後，使用相同測試題能檢查模型行為是否改變；以實際模型做抽样驗證，不以關鍵字規則的單元測試取代。
8. 口語 1–3 句與看板內容分離；看板詳情不受同一份短答字數上限擠掉，也不被送入語音。
9. 規則要求破壞格式、模型輸出不完整、輸出只有看板或插話取消時，仍保有協定驗證與輪次隔離。
10. 已顯示項目能支援「第二點」追問；仅生成但尚未顯示的內容不當成已顯示。

實際模型遵循率與延遲須在實作後驗證；此設計文件不承諾尚未測得的數據。
